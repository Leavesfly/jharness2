# 存储层扩展技术方案

## 1. 背景与目标

JHarness2 作为多用户 AI Agent Web 服务，当前存储层仅覆盖用户账户、会话历史、用户记忆三个实体。随着服务规模扩大，需要在**用量计量、审计合规、语义检索、任务持久化、数据治理**等方面补齐能力。

### 设计原则

- **依赖倒置**：能力接口定义在 core 层（`core.spi`），实现在 storage 层
- **渐进引入**：按优先级分阶段落地，低优先级能力不阻塞高优先级
- **对引擎透明**：engine 层零侵入，所有扩展通过 core SPI 注入

### 依赖方向（不变）

```
engine ← core（定义 SPI 接口） ← storage（提供实现） ← web（组装 + API）
```

## 4. 详细设计

### 4.1 用量持久化与聚合查询（P0）

#### 现状分析

当前 `UsageAggregator` 是纯内存实现（`ConcurrentHashMap`），服务重启后数据丢失，无法支持按月统计、历史趋势等场景。

#### Core 层接口

**文件**：`core/src/.../core/spi/UsageStore.java`

```java
package io.leavesfly.jharness2.core.spi;

import io.leavesfly.jharness2.core.quota.UsageRecord;
import java.time.LocalDate;
import java.util.List;

/**
 * 用量数据持久化 SPI。
 * <p>
 * 支持写入用量记录和按维度聚合查询，供 QuotaPolicy 做超限判断，
 * 供管理接口做用量报表。
 */
public interface UsageStore {

    /** 写入一条用量记录 */
    void record(UsageRecord record);

    /** 查询用户指定日期的总 token 用量 */
    long getDailyTokens(String userId, LocalDate date);

    /** 查询用户指定月份的总 token 用量 */
    long getMonthlyTokens(String userId, int year, int month);

    /** 查询用户指定日期范围内的用量明细 */
    List<UsageRecord> queryRecords(String userId, LocalDate from, LocalDate to);

    /** 按模型维度聚合统计 */
    List<ModelUsageSummary> getModelUsageSummary(String userId, LocalDate from, LocalDate to);
}
```

**文件**：`core/src/.../core/spi/ModelUsageSummary.java`

```java
public record ModelUsageSummary(
    String model,
    long inputTokens,
    long outputTokens,
    int requestCount
) {}
```

#### Storage 层实现

**Entity**：

```sql
CREATE TABLE usage_records (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id       VARCHAR(64)  NOT NULL,
    session_id    VARCHAR(64)  NOT NULL,
    model         VARCHAR(128) NOT NULL,
    input_tokens  BIGINT       NOT NULL DEFAULT 0,
    output_tokens BIGINT       NOT NULL DEFAULT 0,
    recorded_at   TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,

    INDEX idx_usage_user_date (user_id, recorded_at),
    INDEX idx_usage_model (model, recorded_at)
);
```

**改造点**：`UsageAggregator` 改为组合模式 —— 内存缓存（实时限流判断）+ `UsageStore`（异步刷盘持久化）。

#### 集成方式

```
ChatInterceptor.afterChat()
    → UsageAggregator.record(record)     // 内存实时更新
        → UsageStore.record(record)      // 异步持久化（可用队列削峰）
```

### 4.2 工具执行审计日志（P0）

#### Core 层接口

**文件**：`core/src/.../core/spi/ToolAuditLogger.java`

```java
package io.leavesfly.jharness2.core.spi;

import java.time.Instant;
import java.util.List;

/**
 * 工具执行审计日志 SPI。
 * <p>
 * 记录 Agent 每次工具调用的输入/输出/结果，
 * 用于安全审计、故障排查、行为分析。
 */
public interface ToolAuditLogger {

    /** 记录一次工具执行 */
    void log(ToolAuditEntry entry);

    /** 按用户+时间范围查询审计日志 */
    List<ToolAuditEntry> query(String userId, Instant from, Instant to, int limit);

    /** 按会话查询审计日志 */
    List<ToolAuditEntry> queryBySession(String userId, String sessionId);
}
```

**文件**：`core/src/.../core/spi/ToolAuditEntry.java`

```java
public record ToolAuditEntry(
    String id,
    String userId,
    String sessionId,
    String toolName,
    String arguments,       // JSON，可截断存储
    String result,          // JSON，可截断存储
    String status,          // SUCCESS / FAILED / TIMEOUT / DENIED
    String riskLevel,       // LOW / MEDIUM / HIGH / CRITICAL
    long durationMs,
    Instant executedAt
) {}
```

#### Storage 层 Entity

```sql
CREATE TABLE tool_audit_logs (
    id          VARCHAR(36)  PRIMARY KEY,  -- UUID
    user_id     VARCHAR(64)  NOT NULL,
    session_id  VARCHAR(64)  NOT NULL,
    tool_name   VARCHAR(128) NOT NULL,
    arguments   TEXT,
    result      TEXT,
    status      VARCHAR(16)  NOT NULL,
    risk_level  VARCHAR(16)  NOT NULL DEFAULT 'LOW',
    duration_ms BIGINT       NOT NULL DEFAULT 0,
    executed_at TIMESTAMP    NOT NULL,

    INDEX idx_audit_user_time (user_id, executed_at),
    INDEX idx_audit_session (user_id, session_id),
    INDEX idx_audit_tool (tool_name, executed_at)
);
```

#### 集成方式

通过 `EngineCustomizer` 注册一个工具执行拦截器，在工具 before/after 阶段自动记录：

```
EngineCustomizer (AuditCustomizer)
    → 注册 ToolExecutionHook
        → before: 记录开始时间、参数
        → after:  计算耗时、记录结果 → ToolAuditLogger.log()
```

#### 风险等级自动判定规则

| 工具类型 | 风险等级 |
|---------|---------|
| 文件读取 (read_file, list_dir) | LOW |
| 搜索 (grep, codebase_search) | LOW |
| 文件写入 (create_file, file_replace) | MEDIUM |
| 命令执行 (launch-process) | HIGH |
| 网络请求 (web_fetch) | MEDIUM |
| 删除操作 (delete_file) | HIGH |

### 4.3 会话消息结构化拆分（P1）

#### 现状问题

当前 `messagesJson` 以 LONGTEXT 存整个 JSON，会话超过 100 轮后：
- 每次读写都需要完整反序列化/序列化
- 无法按消息角色过滤、分页查询
- 单条记录可能超过 16MB（MySQL LONGTEXT 实际瓶颈在传输层）

#### 方案

**新增 `chat_messages` 表**，对 core 层 `SessionPersistenceService` 接口**保持不变**（向后兼容），storage 内部做拆分。

```sql
CREATE TABLE chat_messages (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id     VARCHAR(64)  NOT NULL,
    session_id  VARCHAR(64)  NOT NULL,
    seq_no      INT          NOT NULL,  -- 消息序号（从0开始）
    role        VARCHAR(16)  NOT NULL,  -- user / assistant / tool / system
    content     MEDIUMTEXT   NOT NULL,  -- 单条消息内容(JSON)
    token_count INT          NOT NULL DEFAULT 0,
    created_at  TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,

    UNIQUE INDEX idx_msg_session_seq (user_id, session_id, seq_no),
    INDEX idx_msg_role (user_id, session_id, role)
);
```

**改造策略（双写迁移）**：
1. 第一阶段：写入时同时写 `chat_messages` + `messagesJson`（兼容）
2. 第二阶段：读取优先从 `chat_messages` 分页加载
3. 第三阶段：`messagesJson` 字段废弃，仅保留元数据

**对 core 层透明**：`SessionPersistenceService.saveSession()` 签名不变，storage 内部决定如何存储。

### 4.4 异步任务状态持久化（P1）

#### Core 层接口

**文件**：`core/src/.../core/spi/TaskStateStore.java`

```java
package io.leavesfly.jharness2.core.spi;

import java.time.Instant;
import java.util.List;
import java.util.Optional;

/**
 * 后台任务/Sub-Agent 任务状态持久化 SPI。
 * <p>
 * 支持任务状态追踪、故障恢复、超时检测。
 */
public interface TaskStateStore {

    /** 创建任务记录 */
    void create(TaskState task);

    /** 更新任务状态 */
    void updateStatus(String taskId, TaskStatus status, String output);

    /** 查询任务 */
    Optional<TaskState> findById(String taskId);

    /** 查询用户的活跃任务 */
    List<TaskState> findActiveTasks(String userId);

    /** 查询超时任务（用于恢复/清理） */
    List<TaskState> findTimedOutTasks(Instant timeoutBefore);

    /** 标记任务重试 */
    void incrementRetry(String taskId);
}
```

**文件**：`core/src/.../core/spi/TaskState.java`

```java
public record TaskState(
    String taskId,
    String userId,
    String sessionId,
    String parentTaskId,    // null 表示顶层任务
    String type,            // BACKGROUND / SUB_AGENT / SCHEDULED
    TaskStatus status,      // PENDING / RUNNING / COMPLETED / FAILED / CANCELLED
    String input,           // 任务输入描述
    String output,          // 任务输出结果
    int retryCount,
    int maxRetries,
    Instant createdAt,
    Instant updatedAt,
    Instant timeoutAt       // 超时截止时间
) {}
```

**文件**：`core/src/.../core/spi/TaskStatus.java`

```java
public enum TaskStatus {
    PENDING, RUNNING, COMPLETED, FAILED, CANCELLED, TIMED_OUT
}
```

#### Storage 层 Entity

```sql
CREATE TABLE agent_tasks (
    task_id        VARCHAR(36)  PRIMARY KEY,
    user_id        VARCHAR(64)  NOT NULL,
    session_id     VARCHAR(64),
    parent_task_id VARCHAR(36),
    type           VARCHAR(32)  NOT NULL,
    status         VARCHAR(16)  NOT NULL DEFAULT 'PENDING',
    input          TEXT,
    output         TEXT,
    retry_count    INT          NOT NULL DEFAULT 0,
    max_retries    INT          NOT NULL DEFAULT 3,
    created_at     TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at     TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    timeout_at     TIMESTAMP,

    INDEX idx_task_user_status (user_id, status),
    INDEX idx_task_timeout (status, timeout_at)
);
```

#### 集成方式

```
BackgroundTaskManager.submit(task)
    → TaskStateStore.create(taskState)           // 持久化
    → executor.submit(task)
        → onStart: TaskStateStore.updateStatus(RUNNING)
        → onComplete: TaskStateStore.updateStatus(COMPLETED, result)
        → onFail: TaskStateStore.updateStatus(FAILED, error)

服务启动时:
    → TaskStateStore.findActiveTasks() → 恢复 RUNNING 状态的任务
```

### 4.5 向量语义检索（P2）

#### Core 层接口

**文件**：`core/src/.../core/spi/VectorMemorySearch.java`

```java
package io.leavesfly.jharness2.core.spi;

import java.util.List;

/**
 * 向量语义搜索 SPI —— 增强记忆检索能力。
 * <p>
 * 将文本 embedding 化后做相似度检索，
 * 替代纯 LIKE 关键词匹配，提升记忆召回的准确性。
 */
public interface VectorMemorySearch {

    /** 索引一条记忆（生成 embedding 并存储） */
    void index(String userId, String project, String memoryId, String content);

    /** 语义搜索：返回与 query 最相似的 topK 条记忆 ID */
    List<VectorSearchResult> search(String userId, String project, String query, int topK);

    /** 删除指定记忆的向量索引 */
    void delete(String memoryId);

    /** 批量重建用户的向量索引 */
    void rebuildIndex(String userId, String project);
}
```

**文件**：`core/src/.../core/spi/VectorSearchResult.java`

```java
public record VectorSearchResult(
    String memoryId,
    double score,       // 相似度分数 [0, 1]
    String snippet      // 匹配的文本片段（可选）
) {}
```

#### Storage 层实现方案（可选后端）

| 方案 | 适用场景 | 依赖 |
|------|---------|------|
| **pgvector** (PostgreSQL 扩展) | 中小规模，记忆 < 100万条 | PostgreSQL 15+ |
| **Milvus / Qdrant** | 大规模，需要高性能召回 | 独立向量数据库 |
| **内嵌 HNSW** (本地文件) | 开发/测试，单机部署 | lucene-core |

#### Embedding 策略

- 使用与 LLM 同源的 Embedding API（OpenAI `text-embedding-3-small` 或兼容接口）
- 向量维度：1536（OpenAI）或 1024（本地模型）
- 存储：`memory_vectors` 表 或 向量库 collection

```sql
-- pgvector 方案
CREATE TABLE memory_vectors (
    memory_id  VARCHAR(64) PRIMARY KEY,
    user_id    VARCHAR(64) NOT NULL,
    project    VARCHAR(128),
    embedding  vector(1536),   -- pgvector 类型
    content    TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_vector_user ON memory_vectors USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100);
```

#### 集成方式

```
MemoryStorageService.saveMemory()
    → MemoryRepository.save()                 // 原有逻辑不变
    → VectorMemorySearch.index()              // 异步生成 embedding 并索引

MemoryStorageService.searchMemories()
    → VectorMemorySearch.search(query, topK)  // 语义召回候选
    → MemoryRepository.findAllById(ids)       // 加载完整记忆内容
```

### 4.6 多租户/组织模型（P2）

#### 定义层：web 层

多租户是业务身份层面的概念，与引擎运行时无关，定义在 web 层。

#### 数据模型

```sql
CREATE TABLE organizations (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    org_id      VARCHAR(64)  NOT NULL UNIQUE,
    name        VARCHAR(128) NOT NULL,
    quota_plan  VARCHAR(32)  NOT NULL DEFAULT 'STANDARD',  -- 组织级配额计划
    enabled     BOOLEAN      NOT NULL DEFAULT TRUE,
    created_at  TIMESTAMP    DEFAULT CURRENT_TIMESTAMP

-- users 表新增字段
ALTER TABLE users ADD COLUMN org_id VARCHAR(64) DEFAULT NULL;
ALTER TABLE users ADD INDEX idx_user_org (org_id);
```

#### 隔离策略

| 层级 | 隔离粒度 | 实现方式 |
|------|---------|---------|
| 数据隔离 | 组织间数据完全不可见 | 所有查询自动附加 `org_id` 条件 |
| 配额隔离 | 组织级共享配额池 | `QuotaPolicy` 支持组织维度聚合 |
| 工作空间 | 组织级目录隔离 | `workspaces/{orgId}/{userId}/` |

### 4.8 数据生命周期管理（P3）

#### 定义层：storage 自治

不需要 core 层接口，由 storage 内部定时任务自行管理。

#### 策略

```yaml
jharness2:
  storage:
    lifecycle:
      session-archive-after-days: 90      # 90天未更新的会话归档
      audit-log-retain-days: 180          # 审计日志保留180天
      usage-detail-retain-days: 365       # 用量明细保留1年
      soft-delete-purge-after-days: 30    # 软删除30天后物理清除
```

#### 实现

```java
@Component
public class DataLifecycleScheduler {

    @Scheduled(cron = "0 0 3 * * ?")  // 每天凌晨3点
    public void executeLifecyclePolicies() {
        archiveOldSessions();
        purgeExpiredAuditLogs();
        cleanupSoftDeleted();
    }
}
```

#### 归档方案

- 冷会话 → 压缩后写入对象存储（OSS），本地 DB 仅保留元数据
- 用户请求查看历史会话时 → 从 OSS 按需加载

## 6. 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 审计日志与消息分离 | 独立表 | 审计有独立生命周期、索引需求，混在 messagesJson 里无法独立查询 |
| 用量写入方式 | 内存缓冲 + 异步刷盘 | 避免每次 LLM 调用都产生 DB 写入，削峰 |
| 向量库选型 | pgvector 优先 | 与现有 JPA 生态一致，中小规模够用，不引入额外基础设施 |
| 消息拆分策略 | 双写迁移 | SessionPersistenceService 接口不变，对 core 层零侵入 |
| 多租户隔离 | 逻辑隔离（同库同表） | 团队内部服务，物理隔离过重 |
| 任务状态 | 乐观更新 + 超时兜底 | 避免分布式锁复杂度，超时任务由定时扫描恢复 |
